# Аудит GPM перед подготовкой к запуску

Дата проверки: 25.08.2026 (Europe/Moscow)

## Итог

Текущее приложение нельзя считать готовым к пилоту на реальных данных. Оно
подходит только для закрытого тестирования на вымышленных профилях и заказах.
Главная причина — не внешний вид, а смешение production API с локальной
демо-логикой.

До этой проверки интерфейс создавал впечатление, что все функции серверные, но
фактически:

- одна общая учётная запись позволяла выбрать любую роль;
- `/app-api/me/orders` не разделял данные по владельцам и ролям;
- клиентский ручной заказ не отправлялся на сервер и исчезал после синхронизации;
- отклики, назначения, профили, финансы и чаты оставались в памяти браузера или
  `localStorage`;
- в API сохранялся и возвращался полный исходный `source_payload`, включая
  потенциально лишние персональные данные;
- production мог молча использовать небезопасные placeholders либо SQLite;
- автоматических backend-, widget- и integration-тестов не было.

## Фактические контуры проекта

1. Активный Flutter web: `lib/main.dart`, `lib/screens/**`,
   `lib/services/gpm_api_service.dart`.
2. Активный FastAPI API: `app/app_orders_api.py`.
3. Legacy Telegram-бот: `main.py`, `app/handlers/**`, `app/services/**`.
4. Набор старых и дублирующих Flutter-экранов: `lib/client/**`,
   `lib/worker/**`, `lib/logist/**`, примеры и корневые старые экраны.

Из 50 Dart-файлов только около половины достижимы из текущего `main.dart`.
Legacy-бот не должен включаться как запасной production-канал: он требует
отдельной переработки авторизации, webhook, обработки паспортов и ПДн.

## Исправления этой ветки

- Ручные клиентские заказы в API-режиме теперь отправляются на backend.
- Источник заказа (`manual`, `external`, `crm`) отделён от факта публикации.
- Повторный импорт больше не должен стирать статус, назначения и отклики.
- Полный исходный `source_payload` больше не сохраняется для новых заказов и не
  возвращается через пользовательский API.
- Клиентская выдача ограничена заказами с соответствующим `created_by`;
  неназначенный исполнитель видит только опубликованные заказы без точного
  адреса, координат, владельца и контактов, а активные/завершённые заказы —
  только после назначения.
- Роль больше не принимается от экрана входа: backend назначает её по
  серверной конфигурации отдельной учётной записи клиента, исполнителя или
  логиста. Это безопасный переходный режим, но ещё не полноценная модель
  пользователей в БД.
- Публичный PATCH ограничен статусом, неизвестные поля и статусы дают ошибку.
- Повторный публичный POST с существующим ID возвращает `409`, а изменение
  состояния и сохранение выполняются атомарно (`SELECT ... FOR UPDATE` в
  PostgreSQL, `BEGIN IMMEDIATE` в SQLite), чтобы не терять параллельные правки.
- Интеграционный токен и JWT placeholders теперь закрывают доступ, а не дают
  небезопасный fallback.
- JWT проверяет алгоритм и минимальную длину секрета.
- `/health` выполняет реальный `SELECT 1`.
- В production-режиме backend требует PostgreSQL, явные CORS origins и
  настроенные секреты.
- Синхронные DB-операции активных async endpoints вынесены из event loop.
- Сетевые вызовы Flutter получили timeout; ошибки синхронизации больше не
  превращаются молча в пустые списки.
- Истечение/отказ сессии возвращает приложение к входу, а сообщение пользователю
  не раскрывает сырой ответ backend.
- Из UI убраны публичные `admin/admin` и заранее заполненный логин.
- Добавлена честная пометка закрытого тестирования и запрет ввода реальных
  чувствительных данных.
- Немецкая статическая карта, получавшая точные координаты из браузера,
  отключена.
- Исправлены web metadata, язык страницы, PWA-название и Android INTERNET.
- Основной красный цвет затемнён до контраста, достаточного для белого текста.
- Форма заказа проверяет будущую дату (от 30 минут до года), часы, число
  исполнителей, вес и этаж; метро стало необязательным. Blanket-фильтр
  гражданства отключён и заменён нейтральным требованием законного права на
  работу.
- Legacy Telegram-бот по умолчанию заблокирован явным opt-in.
- Добавлены первые backend- и Flutter widget-тесты.
- CI проверяет backend, PostgreSQL health и точный SHA, использует сетевые
  таймауты/обработку прерывания и выполняет backend rollback при неуспешном
  restart/health.
- Demo workflow больше не может случайно опубликовать произвольный `DEMO_ENV`.
- Активный API переведён с FastAPI `0.115.6` и уязвимого допустимого диапазона
  Starlette `0.40–0.41` на FastAPI `0.141.1` + Starlette `1.6.0`; обновлены
  Uvicorn, PyYAML и psycopg2-binary, добавлен транзитивный lock и `pip-audit` в
  CI.
- Все сторонние GitHub Actions обновлены и закреплены на полных commit SHA;
  добавлены отдельный CI для веток/PR и Dependabot для Actions, Python и
  Dart/Flutter. Runner закреплён на Ubuntu 24.04 вместо плавающего
  `ubuntu-latest`.
- Localhost CORS ограничен точными origin `localhost:8090` и
  `127.0.0.1:8090`; production-деплой теперь проверяет наличие этих origin в
  серверной конфигурации. На действующий сервер это изменение ещё не
  публиковалось.

Эти изменения уменьшают риск, но не заменяют полноценную серверную модель
пользователей, ролей и рабочих сущностей.

## Блокеры реального пилота

### P0 — обязательны

1. Реальные уникальные пользователи: таблица accounts, надёжные хеши паролей,
   подтверждённые контакты, восстановление и блокировка.
2. Заменить переходные конфигурационные аккаунты на DB-backed accounts. Роль уже
   назначает сервер, а ownership заказов уже ограничен, но нужны полные RBAC и
   tenant checks для каждой сущности и операции.
3. Серверные сущности: client profile, worker profile/verification, order,
   application, assignment, chat и ledger/payment.
4. Удаление production-зависимости от `worker-demo-1`, `_demo*` и общего
   `localStorage`.
5. Довести серверную state machine до полного процесса назначений/откликов и
   добавить неизменяемый audit trail. Базовые допустимые переходы уже
   проверяются сервером.
6. Политика обработки ПДн, оператор, основания, согласия, сроки и удаление.
7. Подтверждённая ротация всех исторически раскрытых секретов.
8. Проверка фактического доступа к уже существующим заказам и журналов как
   потенциального инцидента ПДн.
9. PostgreSQL backup/PITR и проверенное восстановление.
10. E2E-тест изоляции двух клиентов и двух исполнителей.
11. Перед первым деплоем этой ветки сопоставить владельцев всем старым заказам:
    записи без `created_by` новая изоляция намеренно не покажет клиенту. Старый
    `source_payload` очищать только после резервной копии и решения по legal
    hold/проверке инцидента.

### P1 — до публичного запуска

- rate limiting/lockout входа, пагинация и лимиты тела запроса;
- refresh/revocation сессий и безопасная web-модель сессии;
- миграции БД и непривилегированный runtime DB user;
- versioned virtualenv/release для backend-зависимостей с атомарным переключением
  и откатом;
- отдельные deploy users/keys вместо root;
- hash-проверка Python lock-файла (версии уже зафиксированы, но загрузка всех
  platform-хешей завершилась сетевым timeout PyPI);
- совместный rollback frontend/backend либо обязательная политика
  backward-compatible API: текущий deploy `all` не атомарен между компонентами;
- политика retention для backup и мониторинг диска;
- серверные чаты либо удаление заявлений, что переписка хранится GPM;
- реальные финансовые расчёты либо удаление фиктивного баланса/вывода;
- адаптивная desktop-навигация, deep links и browser history;
- accessibility audit на keyboard, screen reader и увеличенном шрифте;
- единый словарь статусов, цен, времени и названий работников;
- очистка недостижимых дублей после подтверждения, что они не нужны.

## Продуктовые несостыковки

- `NEW`, `PROCESSED`, `JUNK`, `DONE_PENDING` называются по-разному у трёх
  ролей; нужен один согласованный словарь и state diagram.
- «Грузчики» используются для такелажников, сборщиков и упаковщиков.
- Право на работу пока только объяснено в UI, но не проверяется сервером.
- Не реализованные чаты, профили, отклики, назначения и финансы теперь честно
  отключены в API-режиме, однако их серверную модель ещё предстоит создать.
- Регистрация пока не реализована; переходные учётные записи выдаются только
  администратором теста.
- Мобильная нижняя навигация и формы без ограничения ширины используются на
  desktop; URL не отражает вкладку и выбранный заказ.

## Тестовый минимум следующего этапа

- unit: JWT/session, схемы, state transitions, permission matrix;
- API integration: client A не видит client B, worker не видит контакты до
  назначения, logist действует только в своей организации;
- concurrency: повторный импорт, два назначения на последнее место, lost update;
- Flutter widget: login, ошибки/offline, формы и доступность;
- E2E: регистрация → заказ → модерация → отклик → назначение → выполнение →
  расчёт → закрытие;
- deployment: точный SHA, миграция, rollback, DB-down и restore drill.

## Выполненные проверки

- `python -m unittest discover -s tests -v`: **14/14 успешно**;
- `flutter test`: **2/2 успешно**;
- `flutter analyze --no-pub`: **No issues found**;
- `flutter build web --release --base-href /`: успешно при выводе в ASCII-путь
  `C:\tmp\gpm-audit-web-20260825`;
- YAML/JSON parsing и `git diff --check`: успешно (только штатные предупреждения
  Windows о будущем преобразовании LF в CRLF).
- публичная read-only проверка production 25.08.2026: frontend — HTTP `200`,
  `/health` — HTTP `200` с `{"status":"ok","storage":"postgres"}`, публичный
  Flutter `.env` содержит только `GPM_APP_MODE=api` и URL API.

Эта проверка подтверждает доступность действующей версии, но не означает, что в
неё уже попали исправления этой ветки, и не подтверждает безопасность
авторизации или соответствие требованиям ПДн.

Отдельный dependency-аудит подтвердил, что прежний FastAPI допускал только
уязвимую ветку Starlette; обновлённый lock проверяется через `pip-audit`.
Legacy `requirements.txt` не входит в production API и всё ещё содержит
устаревшие/уязвимые пакеты (`aiohttp 3.8.4`, `PyJWT 1.7.1`, `Twisted 18.9.0` и
другие). Поэтому legacy-бот должен оставаться выключенным до отдельной миграции
на современный стек либо архивирования.

Сборка непосредственно в рабочем пути с кириллицей остановилась в Flutter shader
compiler из-за ограничения пути Windows, а не из-за исходного кода. Для CI/Linux
это не воспроизводится; локально нужен ASCII build-каталог.

## Что сознательно не сделано автоматически

- Production не публиковался.
- Реальные секреты и populated env не читались и не записывались в Git.
- Старые ZIP/SQLite/Chrome backups не удалялись: это возможно только после
  подтверждения точных путей и решения по резервной копии/расследованию.
- Не выдумывались реквизиты оператора, условия оферты, сроки хранения и
  договорная модель.
- Не выбран DaData/Яндекс и не включены внешние адресные сервисы.
