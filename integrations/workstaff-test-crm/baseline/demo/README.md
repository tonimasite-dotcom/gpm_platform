# Минимальная защита TS перед тестами приложения

Актуальная ревизия demo-05 собрана после отдельного live-отключения дебиторки.
Все четыре действующих debt guards сохранены также внутри нового пакета.
Сам полный пакет на рабочую TS еще не применен.
Состав: `audits/crm-ts-demo-rebase-2026-11-10/manifest.json` в корне repo.
Manifest SHA: `b99e16ea5017191df337537018d1c28ae2b9f160984bf7a4d2c2ca73f855adac`.
27 файлов: 24 существующих и три новых класса. Никаких миграций, seed, новых
пакетов, замены Kernel, Order.php, маршрутов, ролей, учеток или правил обмена.

## Поведение

- Ежедневная почта останавливается до работы с данными. Laravel Mail/очередь/Swift
  используют отказ/нулевой транспорт; SMTP-настройки сохранены, отправка не включается флагом.
- SMS, IMAP, банковские HTTP-вызовы, телефония и внешние подсказки/геокодер
  закрыты адресными guards. Ручная внешняя операция получает понятный отказ деморежима.
  Старый getCoordinate сохраняет переданные данные без выдуманных координат.
- Pusher заменяется null-транспортом в runtime. Сами локальные уведомления не удаляются.
- GPM publisher/sync, редактор ставки и ограничения логиста остаются побайтно прежними.
  Существующий minute cron не меняется. Защита не подменяет общий HTTP-клиент GPM.
- Вход CRM сохраняет пароль, captcha, enabled-флаг, проверку кода и JWT. Исправлены
  несовместимый аргумент remember у JWTGuard и принятие кода другого пользователя.
  Эти два ранее найденных исправления теперь необходимы для согласованного входа в CRM.
- Код входа после верного пароля шифруется текущим APP_KEY в private storage (0700/0600).
  HTTP-маршрута получения кодов нет. Root-only CLI читает их по SSH в локальное окно
  владельца на 127.0.0.1 со случайным секретным URL; коды/адреса не пишутся в логи.
  Окно показывает свежий код 10 минут, успешная verify очищает его из ящика.
  Существующая проверка captcha не отключается и в live не подменяется.

## Проверки и ограничения

В demo-05 заново пройдены 80 проверок транспортов/ящика и 31 отказ/возобновление
установки, с сохранением debt guards во всех частичных и завершенных состояниях.
14 actual login/verify/JWT/API и 11+16+35 GPM-сценариев из demo-04 повторно не
запускались: auth/GPM код побайтно прежний, WebKlex отличается только сохраненным
debt guard, Policy только private-профилем/маркером версии. Квитанции и SHA
первоначальных отчетов закреплены в auth-equivalence.json/gpm-equivalence.json.
Сами формы/локальное окно не менялись, проверен новый SSH-путь окна. Private MySQL
в этой ревизии не запускался. Старые 7 проверок localhost UI остаются историческими.
В 15 неиспользуемых legacy-методах отсутствующие типы останавливают вызов до
транспорта. Это отдельное подтверждение отказа, а не доказательство исправности
старого почтового интерфейса. Полная приемка всех функций CRM не заявляется.

Широкий кандидат с 37 миграциями, новой финансовой моделью, 24-часовыми доступами
и документными overlays не переносится. Для нынешних guards/входа эти зависимости
не нужны. Новые правила синхронизации остаются отдельной задачей.

## Выпуск и восстановление

`release_plan.py` / `apply_code.py` без параметров выполняют только dry-run.
Live apply требует конкретного согласованного SHA и свежей сверки/backup:
`python3 apply_code.py --apply --approved-manifest <reviewed SHA>`.
До применения нужно отдельное согласование этого пакета: затронута доставка кодов
и код авторизации. Это не разрешение автоматического выпуска на основании файла.

Установка держит только TS в maintenance, сохраняет владельцев/права и заменяет
файлы атомарно. Затем адресно инвалидирует только 27 TS-скриптов через TS FPM socket,
проверяет null-mailer, auth-флаг, связь GPM, HTTP 401 без JWT и HTTP 200 главной.
Общие FPM/master/cron/MySQL, основная CRM и соседний test не перезапускаются.
При отказе maintenance сохраняется/возвращается. `--resume` допускает только
собственный marker и те же SHA. Автоматического восстановления SMTP-способной
старой версии нет: оно противоречило бы постоянному запрету ежедневных писем.

Backup покрывает только затронутый код, не БД. 24 исходных файла восстановлены
в новую локальную частную папку, SHA совпали, отсутствие трех новых учтено.
Ключ остается отдельно в исходном checkout; ни ключи, ни plaintext-копии не входят в Git.
Текущий backup demo-05 включает уже отключенную дебиторку, SHA
`a27ec1bf78624ea99be495952ec44f3146b265856d504821fc04f6ace6358ab3`.
Перед будущими миграциями/операциями с данными нужен другой согласованный объем backup.

После выпуска владелец запускает `python local_login_inbox.py` на своем компьютере,
вводит обычный логин/пароль/captcha на ts.workstaffcrm.ru и берет код в открытом
локальном окне. Тесты публикации/обновления заявки в живой связке с приложением
и ручная браузерная приемка еще не выполнялись.

## Новая сборка и доказательства

Для текущего состояния используется rebase_after_debt_off.py в новом каталоге
demo-05. Прямой запуск исторического prepare_demo.py отключен; он оставлен как
библиотека проверенных insertions. Старые demo-01/02/03/04 и их отчеты не меняются.
На сервере инструменты demo-tools-20261110-v05; передача кода/файлов не меняет live.
Исходники вне 27 выбранных целей — сохраненный reference, не свежий полный snapshot.
Три текущих debt файла взяты из live после проверки SHA успешного узкого deployment.

Перед применением: release_plan.py сверяет текущие before SHA, after SHA, backup,
auth/GPM evidence, исходные baseline/checker, cron и отсутствие старых TS workers.
Изменения доставки кодов/авторизации по-прежнему требуют отдельного согласования.
