# Постоянная связь исполнителей: подготовка без изменения экранов CRM

## Решение владельца

Исполнитель регистрируется в GPM. Система ищет его по подтвержденному телефону:
один рабочий CRM — связать существующего, нет — создать карточку рабочего,
несколько — не объединять автоматически. После первичной связи использовать
постоянные внутренние ID, а не заново сопоставлять каждый заказ по телефону.
Отклик, утверждение состава и назначение бригадира работают в привычных местах CRM.
Не возвращать снятую панель «Онлайн-табель GPM» и ручные привязки в каждой заявке.

Исходный объем разработки поручен владельцем. Изменения схемы и реальные массовые
записи пока не проводились. Основная CRM не разрешена: разработка и испытания только TS.
GPM PR #32 остается опубликованным; ранее выполненный откат TS не отменяется.

## Проверено в текущих системах

Рабочая регистрация GPM использует приглашения. Телефон рабочего доступен
в профиле, но признак реального подтверждения владения номером отсутствует.
Отдельная registration-preview использует тестовый код 123456 и частное
хранилище черновиков; это не подтверждение телефона и не рабочая регистрация.

Поэтому подключать автоматическое сопоставление к введенному или тестово
подтвержденному номеру нельзя. Владелец получил вопрос о выборе реального
подтверждения: SMS либо код входящим звонком. До решения независимую логику
можно разрабатывать, но записи рабочих в действующей CRM не создавать.

В TS рабочие находятся в users с ролью loader, отдельного постоянного app UUID нет.
Обычное создание через LoaderService дополнительно создает Planning и может
вызывать геокодирование. Фоновый импорт не должен вызывать эти побочные действия.
У нового рабочего нужны структурированные фамилия/имя и определенный филиал;
их нельзя придумывать из произвольного display_name или назначать случайно.

## Подготовленная логика

GpmWorkerMatchPolicy — чистая функция, без БД, HTTP или отправки сообщений.
Она нормализует полный номер: российские 8/+7/10 цифр; международный код
сохраняется полностью. Сравнение по последним 10 цифрам для всех стран запрещено.
Принимается только серверное production-подтверждение SMS/звонка с совпадающим
номером и свежим временем; лабораторный или неподтвержденный телефон не связывается.

Повторная обработка сохраняет уже существующую пару ID, включая смену телефона.
Дубли телефонов между GPM или CRM, удаленная карточка, чужая существующая связь
и совпадение с сотрудником/администратором отправляются на разбор.
Состояние неактивного рабочего не меняется. Пароли, роли, банковские реквизиты,
выплаты, старые часы и история существующей карточки не перезаписываются.
Общий work_phone не используется как личный номер.

## Предлагаемый следующий объем

1. Подключить реальное подтверждение телефона к рабочей регистрации/профилю,
   с одноразовым доказательством на сервере, сроком, ограничением попыток
   и аннулированием подтверждения при смене номера. Тестовый код не переносить.
2. Закрытый обмен GPM → TS только подтвержденными рабочими и разрешенными
   полями. Постоянную обратную связь ID хранить в уже существующей таблице
   gpm_app_crm_worker_links GPM: новую такую же таблицу в GPM не создавать.
3. Для TS подготовить отдельное служебное хранилище постоянной пары app UUID /
   users.id и состояния конфликтов. До миграции отдельно представить точную
   схему, последствия для действующих записей, проверенный backup и откат.
   Техническое имя/схема еще не утверждены, миграция не подготовлена.
4. Фоновая обработка должна быть повторяемой: после сбоя не создавать
   второго рабочего; уникальная пара ID, взаимное исключение при одновременном
   импорте и повторная проверка кандидатов перед записью обязательны.
   Частичный сбой между системами восстанавливается через повторную доставку.
5. Синхронизировать состав/старшего в существующем обмене опубликованных
   CRM-заказов; не создавать новый планировщик. UI и обычные действия логиста
   сохранить. Вопрос откликов/подтверждения состава разбирать отдельно от
   первичного создания карточек, не назначать всех зарегистрированных на заказы.
6. Перенос фактических QR-отметок в существующий CRM-табель требует отдельного
   согласованного сопоставления полей. Финансовые часы и начисления автоматически
   не изменять. Постоянная связь людей не заменяет этот обмен.

## Текущий результат и ограничения

Ветка содержит только политику сопоставления, синтетические тесты и этот план.
Никакой production-обмен не включен, схемы/рабочие данные/экраны не менялись.
Правило интерфейса: текущий вид CRM остается, дополнительные панели не возвращать.
Не выдавать подготовленную политику за готовую синхронизацию.

Основную CRM не трогать без отдельного явного согласования.
Очистка заявок не разрешает удалять схему, аккаунты, авторизацию, аудит,
конфигурации, секреты, backup и инфраструктуру. Жизненно важные компоненты
на этом этапе не менялись. Закрытые локаторы и пользовательские данные
в публичный Git не помещать.
