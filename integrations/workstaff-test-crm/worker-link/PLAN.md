# Тестовая регистрация GPM → рабочие TS

## Согласованный объем

Владелец поручил постоянную связь исполнителей по телефону с сохранением
привычного интерфейса CRM. Последнее решение: на тестовой регистрации
использовать общий тестовый код для всех участников, SMS подключить позднее.
Снятые панель онлайн-табеля и ручные привязки в заявках не возвращать.
Основная CRM не разрешена; вся CRM-часть работает только в TS.

## Реализация PR #33

Существующая отдельная анкета registration-preview сохраняет код 123456.
После ее завершения профиль остается тестовым и не получает аккаунт/JWT
основного GPM. Новый закрытый GPM-маршрут экспортирует только завершенные
тестовые профили для TS с service-auth, явными protocol/environment и
серверной отметкой test_code. Публичные токены анкеты доступа к нему не дают.

Существующее ежеминутное задание TS получает новые завершенные анкеты.
По полному нормализованному личному телефону оно:
- связывает единственного существующего рабочего;
- создает новую тестовую карточку, если совпадения нет;
- оставляет дубли, удаленную карточку, сотрудника/администратора и чужую
  существующую связь на разбор, без автоматического объединения.

Постоянная тестовая пара preview profile ID / CRM users.id хранится в закрытых
серверных квитанциях. Файлы 600, каталоги 700, запись атомарная и под блокировкой.
Восстановление после потерянного HTTP-ответа или квитанции не создает второго
рабочего: у новых тестовых карточек есть детерминированный уникальный
технический email в домене .invalid. Почта и SMS не отправляются, пароль CRM
не задается. Только новые карточки получают роль loader; существующие роли,
активность, пароли, реквизиты, деньги и история не меняются.

Филиал новой карточки определяется по городу анкеты и точному названию
компании «Джи Пи ЭМ». Другие компании/ИП/клининг и именные филиалы не выбираются.
При неоднозначности запись откладывается. При нескольких городах используется
первый подходящий в стабильном порядке каталога. Телефон международного формата
сравнивается целиком, не только по последним 10 цифрам.

Обработка запускается в существующей команде обмена; новых cron/очередей нет.
Новых таблиц, миграций и изменений Vue/JS/CSS CRM нет. Существующий LoaderService
не вызывается: его создание Planning и геокодирование здесь не нужны.
Новый тестовый рабочий помечен в существующем поле примечания.

## Изоляция от рабочего режима

Тестовые ID остаются в пространстве registration-preview. Они не записываются
в gpm_app_crm_worker_links, поскольку там нужен настоящий аккаунт GPM.
Тестовый код не подтверждает реальное владение телефоном и не принимается
production-политикой GpmWorkerMatchPolicy. Реальная связь рабочих аккаунтов
с этой таблицей и реальный SMS-провайдер остаются будущим этапом.
Не выдавать тестовый этап за готовую production-регистрацию.

GPM_EXPORT-флаг и TS_IMPORT-флаг по умолчанию выключены. Для TS требуется
правильный APP_URL и отдельная тестовая БД. Есть обязательная начальная дата
испытания: старые завершенные анкеты до нее автоматически не импортируются.
Пересылка через HTTPS без redirect; токен остается на серверах, в браузер не попадает.
Выгружаются ФИО, личный телефон, дата рождения и выбранные города — без паспортных,
банковских сведений, паролей и токенов анкеты. Конфликты повторяются с задержкой.

## Проверки и выпуск

Подготовлены PHP-проверки production-политики, отдельной test-политики и
сервиса с потерянными ответами/квитанциями, откатом создания при отказе роли,
дублями и защитой другой CRM. Python проверяет экспорт/ack, повторные попытки,
изоляцию хранилища/токенов, общий код разных участников, флаги и установщик.

install_preview.py проверяет только TS и отдельную test-БД, сохраняет
исходники/конфигурацию, устанавливает три класса и вызов существующего обмена.
При установке импорт остается выключенным. Перед включением нужны зеленая CI,
свежий GPM backup, закрытая копия затрагиваемых данных TS, проверка runtime
и отдельное включение флагов. Для TS не требуется сборка frontend.
Backend-only выпуск GPM сохраняет frontend и действующую бригадную функцию.

При откате выключить импорт, восстановить прежнюю команду/классы/настройки
через проверенный receipt. Созданные тестовые карточки и квитанции не удалять
автоматически. Ранее сохраненный снимок снятой панели табеля остается архивом;
его возврат после новых изменений требует повторной сверки настроек.

Основную CRM не трогать без отдельного явного согласования.
Очистка заявок не разрешает удалять схему, аккаунты, авторизацию, аудит,
конфигурации, секреты, backup и инфраструктуру. В этом объеме изменяются
серверный API GPM и файлы TS, без миграций. Закрытые локаторы и пользовательские
данные в публичный Git не помещать. Копий проекта на C: не создавать.
