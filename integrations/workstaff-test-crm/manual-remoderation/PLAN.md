# Повторная ручная модерация TS → GPM

Поручение 24.11.2026: каждое ручное повторное отправление заявки до начала
работ должно снова попадать в «На модерации». Владелец отдельно уточнил:
начатые и закрытые заявки не возвращать на модерацию.

Изменяется только ручной publisher TS. Ежеминутный GpmAppOrderSync не вызывает
повторную модерацию и сохраняет состояние. Перед повтором publisher проверяет
владельца и стадию; после синхронизации вызывает отдельный service-auth POST
GPM. Для каждого ручного действия создается новый случайный request_id.
Повтор того же сетевого запроса идемпотентен и не отменяет более позднее одобрение.

GPM проверяет источник TS, активного корпоративного логиста по ID и владельца,
блокирует строку заявки, отклоняет начатые/закрытые статусы и признаки учета
работ/оплаты. Для NEW/PROCESSED меняет только status на NEW. Исполнители, отклики,
номера, реквизиты и прочие поля не очищаются. Операция и прежний статус пишутся
в существующий аудит в той же транзакции. Новых таблиц и миграций нет.
Заявка до повторного одобрения не предлагается исполнителям как одобренная.

Установка: сначала backend GPM после CI/backup, затем только PHP publisher TS.
Не изменять основной CRM, JS/Vue TS, cron, scheduler, SMTP, аккаунты и права.
Перед заменой TS проверить сервер/APP_URL, точный исходный SHA и приватную
точечную копию старого publisher; выполнить PHP 7.4 lint и синтетические проверки
в закрытой папке TS, проверить возврат файла на частной репетиции.
Не размещать среду GPM или SDK на сервере TS.

Откат кода: вернуть только прежний publisher из проверенной копии и при
необходимости прежний backend штатным способом. Кодовый откат не должен
автоматически возвращать прошлые статусы: после ручных действий владельца
сохранить актуальные заявки и аудит, данные восстанавливать только по
отдельному согласованному разбору. Реальные заявки автоматически не переотправлять.
