# QR-табель GPM → TS

Объем отдельно согласован владельцем 23.11.2026: три новые таблицы в существующей
PostgreSQL GPM, сбор бригады по QR, индивидуальные время/геолокация, ручные решения
логиста и передача фактических отметок в TS. Основная CRM не затрагивается.

## Порядок работы

1. Исполнители должны иметь собственные профили GPM и быть назначены на заявку.
2. Во вкладке «Рабочие» TS логист явно связывает каждого рабочего с его профилем
   GPM. Имя и последние цифры телефона помогают проверить выбор; автоматической
   привязки по имени или телефону нет. Неправильную связь нельзя молча заменить.
3. Для двух и более исполнителей назначается бригадир существующей кнопкой CRM.
   Уже назначенного рабочего можно выбрать старшим и при заполненных местах.
4. «Обновить старшего» передает назначение; при различии составов требуется
   явное подтверждение состава. Рабочего с записанными отметками снять нельзя.
5. «Включить QR-табель» доступно до начала учета по прежней схеме. Начатые
   смены продолжаются по прежним правилам. Для заявок приложения настройка
   доступна своему логисту в GPM.
6. Старший начинает сбор прихода/ухода, сканирует одноразовый QR каждого рабочего
   и показывает итоговый QR клиенту. Клиент подтверждает зафиксированный список.
   При одном исполнителе клиент сканирует QR самого исполнителя.
7. Поздний приход и ранний уход проводятся отдельным сбором. В табеле сохраняется
   индивидуальное серверное время сканирования, а не общее время подтверждения.
8. Нет разрешения на геолокацию, плохая точность, старая точка, удаленность или
   отсутствие точки объекта направляют отметку своему логисту. После подтверждения
   клиентом логист принимает решение с обязательной причиной. Время не редактируется.
9. Фактические отметки видны в GPM и в панели «Онлайн-табель GPM» TS. Оплачиваемые
   часы Planning/ReportCard, ставки, премии и начисления этим адаптером не меняются.

В профиле отправителя TS по-прежнему обязателен сохраненный ID логиста GPM.
Он проверяется сервером при каждом обмене, телефон и ID из браузера его не заменяют.
Служебный токен хранится только на сервере TS.

## Хранение и проверки

В GPM добавляются только таблицы связей рабочих, сборов и QR/геоподтверждений.
Прежний журнал прихода/ухода остается источником подтвержденного времени.
Сохраняются история решений и подтвержденные записи. Неподтвержденные QR
истекают; повторное использование блокируется. Геолокация запрашивается
однократно при действии, фонового отслеживания нет. Начальные пороги:
QR 60 секунд, сбор 15 минут, точность 100 м, радиус объекта 200 м,
свежесть измерения 30 секунд.

TS получает ограниченный снимок по своей заявке и хранит его в закрытом кеше.
Версия снимка монотонная: поздний ответ не затирает более новый табель.
Используется существующее задание обмена; новых cron/очередей нет.

## Установка и откат

Сначала проходят серверные проверки SQLite/PostgreSQL, Flutter и проверки адаптера.
Перед выпуском обязателен свежий проверенный backup GPM. Production workflow
принимает crew_attendance=keep|enable|disable; enable открывает настройку,
но не переводит уже идущие смены на новые правила.

prepare.py проверяет только TS, поддерживаемые исходники и все точки замены до
первой записи. install.py резервирует исходники, конфигурацию и веб-ресурсы,
проверяет хеши, собирает интерфейс TS и восстанавливает прежнюю версию при сбое.
Точное расположение созданных резервных копий сохраняется только в закрытом
операционном контексте. Флаг TS включается отдельно после готовности GPM.

Для остановки новых сборов выключить флаг доступности; подтвержденные отметки
и решения логиста остаются доступны. Перед полным возвратом старого API выключить
новые сборы, выполнить python -m app.crew_maintenance на новой версии, затем
восстановить прежний код/среду и frontend. Это погашает неподтвержденные групповые
QR, чтобы старый API не принял их за индивидуальные. Подтвержденные записи,
ожидающие проверки отметки и три новые таблицы не удалять. Для TS используется
проверенный release receipt и install.py --rollback с частным адресом backup.

Основную CRM не трогать. Переход к ней требует отдельного явного согласования.
Очистка заявок не разрешает удалять схему, аккаунты, авторизацию, аудит,
конфигурации, секреты, backup и инфраструктуру. Из жизненно важных компонентов
в этом объеме меняются API и добавляется схема; отдельное согласование получено.
Реальная проверка камер и геолокации на устройствах остается этапом приемки.
