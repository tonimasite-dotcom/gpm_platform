# Двустороннее редактирование заказов тестовой CRM

Пакет предназначен только для `https://ts.workstaffcrm.ru`, физический каталог
`/var/www/gruzpiter/data/www/ts.workstaffcrm.ru`. Основную CRM нельзя изменять
без отдельного предварительного явного согласования владельца.

## Поведение

- Ручная отправка заказа создаёт явную связь с экземпляром тестовой CRM.
- `php artisan gpm:sync-orders` сравнивает текущие общие поля с последними
  принятыми значениями обеих систем. Изменения разных полей объединяются.
- При одновременном изменении одного поля значение **приложения** имеет приоритет.
- PATCH в API содержит версию прочитанного содержимого: новая правка приложения
  отклоняет устаревшую запись CRM с HTTP 409. Следующая попытка читает свежую версию.
- Ошибка связи или сохранения оставляет прежнюю точку сравнения для повторной
  попытки. После принятого PATCH и ошибки CRM-транзакции повтор сходится к
  уже принятому значению приложения.
- Закрытые/отменённые заказы защищены с обеих сторон. Статусы, назначения,
  отклики, часы прихода/ухода, оценки и чаты остаются процессами GPM.
- Новое поведение повторной публикации активных заказов ограничено явным
  `source_instance=https://ts.workstaffcrm.ru`. У остальных/старых издателей
  сохраняются прежние правила: повторная публикация не перезаписывает
  содержимое уже принятого заказа; новый sync-протокол им недоступен.
- Старые заказы подключаются явной повторной отправкой из **тестовой** CRM.
  При включённой синхронизации этот первый шаг сохраняет прежние правки приложения.
  Автоматически искать совпадения с заказами других экземпляров CRM запрещено.

## Общие поля

| Приложение | Тестовая CRM | Направление |
|---|---|---|
| `city`, `address` | `city`, `address` | Оба |
| `scheduled_at` | `completion_date`, тот же момент в UTC | Оба |
| `workers_count` | `loader_count` | Оба |
| `hours`, `min_time` | `duration`, `min_time` | Оба |
| `price_per_hour` | `workers_cost` | Оба |
| `description` | `note` | Оба |
| `metro` | Имя существующей станции по `metro_id` | Оба |
| `address_street`, `address_number` | `street`, `house` | Оба |
| `address_lat`, `address_lon` | `coords` | Оба |
| `additional_info` | Структурированные опции `additional` + свободный текст `info` | Оба; опции CRM сохраняются |
| `price_regular`, `price_state` | Общая ставка `workers_cost` | CRM → приложение; отдельные ставки GPM не затираются без нового изменения CRM |
| `individual_price`, `legal_price` | `customer_cost` | CRM → приложение; логисту запрещено менять эти бюджеты |

Название приложения, гражданство для отбора, режим смены и описание смены не
имеют отдельных столбцов в существующей CRM и остаются полями GPM. Поэтому
интеграция синхронизирует **общие поля заказа**, а не делает базы идентичными.
Для переноса этих дополнительных полей в интерфейс CRM нужна отдельная правка
её формы и модели. Неизвестное или неоднозначное метро откладывает синхронизацию
заказа, сохраняя данные, вместо изменения справочника.

## Установка и включение

**Состояние на 15.10.2026:** пакет и API выпущены, ts-флаг включён, отдельный
минутный cron установлен. Не повторять установку/активацию без причины.
Точные результаты, backups, выполненная привязка 005/26 и команды —
`PROJECT_HANDOFF_2026-10-15_PRODUCTION_TESTER_RELEASE.md` в корне репозитория.
`probe-test-crm.php` и `inspect-unlinked-orders.php` читают состояние;
`enable-test-crm.py` и `link-test-order.php` по умолчанию делают dry run.
Последний требует подтверждённого происхождения старого заказа из ts для
`--apply --confirmed-test-origin`. Совпадение номера не является подтверждением.

1. Выпустить проверенный backend GPM с протоколом `gpm-crm-sync-v1`; сохранить
   проверенный backup БД и конфигурации GPM перед выпуском. Для ручной проверки
   исправлений интерфейса нужен соответствующий frontend того же выпуска.
2. Загрузить пакет в закрытую папку `storage/app` **тестовой** CRM. Выполнить
   `python3 install-test-crm.py` без аргументов: это проверка и план изменений.
   Изменившийся после проверки publisher вызывает остановку для нового сравнения.
3. Выполнить `python3 install-test-crm.py --apply`. Скрипт проверяет синтаксис,
   сценарии, физические пути, выключенный флаг и SHA-256 текущего publisher.
   Перед заменой делает и проверяет копии исходников в `storage/app/gpm-sync-backups`.
   При ошибке восстанавливает изменённые файлы. Схему/данные БД и `.env` не меняет.
4. Перед первым реальным обменом сделать проверенный backup БД **тестовой CRM**.
   На сервере установить `GPM_APP_ORDER_SYNC_ENABLED=true` в её окружении,
   сохранив прежнюю конфигурацию. Секреты не выводить и не переносить в Git.
5. Выполнить от пользователя `gruzpiter` `php artisan gpm:sync-orders` и повторно
   отправить нужный старый тестовый заказ через кнопку публикации. Проверить
   изменение ставки/адреса в обе стороны и одновременные правки.
6. Добавить отдельное минутное cron-задание от `gruzpiter`, вызывающее только
   `/usr/bin/php /var/www/gruzpiter/data/www/ts.workstaffcrm.ru/artisan gpm:sync-orders`.
   Ожидаемая задержка обмена до минуты плюс время запроса. Не включать полный
   Laravel scheduler ради этой задачи: у него есть несвязанные банковские/почтовые jobs.

Файлы связи хранятся в закрытом `storage/app/gpm-app-sync`, данные и логи не
содержат интеграционного токена. Пользователь PHP и cron должен совпадать.

## Проверки и откат

PHP 7.4: `php tests/sync_plan_test.php`, `php tests/sync_service_test.php`.
Тесты используют вымышленные заказы, имитацию сети/БД и уникальную временную папку;
Laravel и рабочая база не загружаются.

Для отката сначала выключить `GPM_APP_ORDER_SYNC_ENABLED` и убрать только cron
синхронизации. Вернуть исходники по проверенному manifest резервной копии;
новые файлы удалять только после сверки с SHA-256 установленной версии.
Резервные копии и файлы связи сохранить. Откат кода не отменяет принятые изменения
заказов: при необходимости восстановление данных проводится отдельно по backup.
