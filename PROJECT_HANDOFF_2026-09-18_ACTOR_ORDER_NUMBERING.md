## 4. Что сделано за сессию 18.09

### 4.1. Диагностика: почему `APP-260918-113134028` всё ещё появлялся

Формат `APP-<yymmdd>-<hhmmssSSS>` — это старая клиентская генерация
(`_generateManualOrderNumber()`), которую фикс `c0f0b53` (11.09) должен был
полностью убрать. Код проверен построчно: текущий `main` действительно
нигде больше не генерирует такой номер на клиенте. Причина в другом —
**`persist_published_order` доверял любому `external_order_id`, который
прислал аутентифицированный клиент**, и перегенерировал номер только если
поле было пустым. Актуальное Flutter-приложение всегда шлёт `null`, поэтому
единственное объяснение — **устаревший, ещё не обновлённый APK** (собранный
до 11.09) на телефоне у реального клиента или логиста, который по-прежнему
генерирует номер сам и отправляет его как есть. Приложение не публикуется
через Google Play (см. раздел 6.4 хендоффа 16.09), автообновления нет,
поэтому такие устройства могут жить сколько угодно долго, пока владелец не
переустановит APK вручную.

**Важно для следующей сессии**: если найдётся, у кого именно стоит старый
APK, у этого же человека, вероятно, не применены и все более поздние
UI-фиксы (батчи 3/4, 09.09–11.09) — стоит попросить его переустановить
`app-release.apk` (актуальная сборка — раздел 4.2 хендоффа 16.09).

### 4.2. Новая схема нумерации заказов — `L#/C#-ДДММГГ-#`

Пользователь предложил, вместо плоского `APP-NNNNNN`, привязать номер к
самому актору: каждый клиент/логист получает постоянный порядковый код при
регистрации (`L1`, `L2`… для логистов; `C1`, `C2`… для клиентов, по
порядку регистрации), и каждый его заказ нумеруется `{код}-{ДДММГГ}-{n}`,
где `n` — счётчик заказов **этого конкретного актора за календарный день**
(сбрасывается на 1 каждый день по Europe/Moscow). Пример: `L1-180926-1`,
следующий заказ этого логиста в тот же день — `L1-180926-2`.

Решения, принятые с пользователем перед реализацией:
- Бэкфилл существующих аккаунтов — по `created_at` (первый
  зарегистрированный получает `1`), разово, до деплоя.
  CRM/интеграционные заказы — новую схему не трогать, у них по-прежнему
  свой обязательный номер извне.
- Заодно закрыть лазейку, которая и привела к багу выше: сервер теперь
  **всегда** сам генерирует номер для аутентифицированного актора и
  полностью игнорирует то, что прислал клиент (не только когда поле
  пустое).

**Реализация** (`app/app_orders_api.py`, `app/backfill_actor_codes.py`,
`tests/test_app_orders_api.py`):
- Три новые таблицы (аддитивно, без `ALTER TABLE`, по конвенции файла):
  `gpm_app_account_actor_codes` (постоянный код аккаунта),
  `gpm_app_actor_code_seq` (счётчик L#/C# по роли),
  `gpm_app_actor_daily_order_seq` (суточный счётчик на актора).
- Код присваивается автоматически в `redeem_account_invitation` (реальная
  регистрация) и `bootstrap_configured_accounts` (сид-аккаунты из конфига).
- `persist_published_order` теперь всегда сам генерирует номер для
  client/logist-актора (падает обратно на старый `APP-NNNNNN`, если у
  аккаунта почему-то ещё нет кода — защитный fallback, не должен
  срабатывать после бэкфилла).
- `app/backfill_actor_codes.py` — разовый (но оставленный в пайплайне,
  см. раздел 3), идемпотентный скрипт: назначает коды всем существующим
  аккаунтам без кода, по `created_at ASC`.
- Часовой пояс: **не** `zoneinfo.ZoneInfo("Europe/Moscow")` — на этой
  машине и потенциально на проде нет пакета `tzdata`, поймано на этапе
  тестирования. Использован фиксированный `timezone(timedelta(hours=3))` —
  Москва не переходит на летнее время с 2014 года, разницы в поведении нет,
  зато не нужна внешняя зависимость.
- Попутно найден и исправлен смежный баг: при перегенерации номера сервер
  обновлял `external_order_id`, но не поле `id` (тот же номер под другим
  ключом, используется для `patch_order_atomically`) — вскрылось на
  существующем тесте `test_role_workspaces_are_server_backed_and_isolated`
  при более широком условии перегенерации. Поправлено — оба поля всегда
  синхронны.

**Тесты**: 58 backend (7 новых: код при регистрации, формат/инкремент
суточного номера, сброс на следующий день, изоляция между акторами,
порядок бэкфилла, идемпотентность бэкфилла, игнорирование клиентского
номера) + 36 Flutter — все зелёные. `flutter analyze` чисто. Плюс ручной
smoke-тест локально и живая проверка через сам факт бэкфилла на проде
(раздел 3).

**Фронтенд не менялся** — `createOrder()` в `gpm_api_service.dart` уже и
раньше просто эхом возвращал то, что прислал сервер, без предположений о
формате. Новая схема невидима для уже установленных APK любой версии —
они как раньше не задают формат, сервер теперь просто жёстче его
контролирует.
