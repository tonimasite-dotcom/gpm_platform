## Решения владельца

1. Рекрутеры и администраторы пока работают через существующие аккаунты логиста;
   новые роли/кабинеты не нужны.
2. Рабочий после первого явного сохранения гражданства не может менять его.
   Логист может; смена гражданства сбрасывает подтверждение паспорта.
3. Тип занятости меняет логист; рабочего лишили такого права.
4. Оплачиваемое время округлять вверх до целого часа, не ниже минимума заказа:
   4 ч 20 мин дают 5 часов. Расчёт отдельно по каждому рабочему.
5. Оценки: «Справился» +1, «Не справился» −2, «С нареканиями» −1,
   «Справился хорошо» +2. Последняя заменяет «Нейтрально».
6. Редактирование заказов синхронизировать в обе стороны. При конфликте
   **одного поля главнее приложение**; разные поля объединять.
7. Все изменения CRM ограничены тестовой `ts.workstaffcrm.ru`. Основная CRM
   требует отдельного предварительного явного согласования.
8. Ошибка отправки из CRM сейчас не воспроизводится: владелец повторно отправил
   заказ, всё прошло. Изображения лучшего качества для логотипа пока нет.

## Важные детали кода и обмена

- Staff GET/PATCH `/app-api/logist/workers/{worker_id}` доступны только логисту.
  Передаются только разрешённые поля, без паспортных/банковских реквизитов.
- Свой профиль не подставляет гражданство автоматически; `nationality_recorded`
  отражает фактическое сохранение. Неизвестное гражданство не допускает отклик
  на заказ с ограничением.
- Клиент редактирует только свой NEW, логист-владелец — NEW/PROCESSED/IN_PROCESS/
  DONE_PENDING. Закрытые/отменённые защищены; бюджеты individual/legal человеку
  менять запрещено; нельзя уменьшить число работников ниже уже назначенных.
- Повторный CRM import обновляет разрешённое содержимое активного заказа,
  сохраняя статусы, назначение, отклики, табель, оценки, владельца, дату создания.
- Табель блокирует сущности в порядке order → challenge → attendance, чтобы
  избежать PostgreSQL deadlock. Устаревший код после отмены не принимается.
- Оценки: POST `/app-api/me/order-reviews/{order_id:path}` с `worker_id`, `result`;
  только логист-владелец для назначенного рабочего в DONE_PENDING.
- Новый интеграционный GET/PATCH `/app-api/integration/order-sync/{order_id:path}`
  требует существующий `X-GPM-App-Token`, проверяет `source_instance`, использует
  SHA-256 revision содержимого и CAS; stale revision — 409. Workflow-поля,
  статусы, отклики, назначения, часы, отзывы этим PATCH не редактируются.
- `source_instance` ограничен `https://ts.workstaffcrm.ru`, чужая привязка — 409.
  Для старого заказа явная публикация с `preserve_existing_content:true`
  сохраняет прежние правки приложения; human actor эту опцию применять не может.
- CRM хранит точки сравнения в `storage/app/gpm-app-sync/{order_id}.json` с
  закрытыми правами; baseline сохраняется после CRM commit. Повтор после сетевой
  ошибки, ошибки commit/сохранения файла сходится, не затирает новые правки.
- Общие поля: город, адрес, дата/время UTC, число рабочих, часы/минимум, ставка,
  описание, существующая станция метро, улица/дом/координаты, доп. сведения.
  Structured CRM options сохраняются; неоднозначное метро откладывает обмен.
  customer_cost → individual/legal только CRM→GPM; правила price_regular/state
  уточнены в README интеграции.
- Название, требование гражданства, work mode и описание смены не имеют колонок
  CRM и остаются в GPM. **Базы не идентичны; обмен относится к общим полям.**
- Связь только явно опубликованных тестовых заказов; не подключать автоматически
  остальные заказы/основную CRM.
- Текущий CRM-пакет проверяет production API URL `https://app-api.gpmbot.ru`.

## Продолжение и ограничения

1. Прочитать этот файл, continuation prompt, текущий handoff, README интеграции
   и фактический `git status`. Сохранить незакоммиченные файлы.
2. Согласовать отдельный тестовый контур GPM: хосты, домены, ресурсы, доступ и
   отдельную БД. Пока это рекомендация, а не выполненный/разрешённый deployment.
3. Для согласованного контура адаптировать whitelist API URL CRM, настроить
   только тестовый экземпляр, выпустить совпадающие backend/frontend с правильным
   публичным API URL и отдельной БД. Выполнить PostgreSQL-проверки.
4. Проверить свежий backup тестовой CRM, затем включать флаг только после
   доступности нового протокола на согласованном endpoint. Добавлять отдельный
   минутный cron только `gpm:sync-orders` от `gruzpiter`. **Не включать целиком
   Laravel scheduler:** в нём несвязанные банковские/почтовые jobs.
5. Привязать старые тестовые заказы явной повторной публикацией, проверить
   обе стороны, конфликт одного поля, разные поля, закрытые заказы, сетевой
   retry. Затем проверить все 12 пунктов, в т.ч. несколько рабочих и QR/финансы.
6. Найти более качественный исходник логотипа. При необходимости переноса
   дополнительных полей в CRM отдельно согласовать её модель/форму.
7. Перед GitHub push/PR проверить auth; не считать публичный GET достаточным.
   Production выпускать только после отдельного согласования, проверенного
   backup PostgreSQL/config и совпадающей версии backend/frontend.

Основную CRM не менять без отдельного предварительного явного согласования.

аккаунты, профили, авторизацию, приглашения, audit, исходники, конфигурацию,
