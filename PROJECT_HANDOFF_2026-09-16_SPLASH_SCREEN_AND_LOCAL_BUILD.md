## 4. Что сделано за сессию 16.09

### 4.1. Дизайн Android-сплэш-экрана (`8d66543`)

Пользователь показал скриншот: при запуске установленного на телефон
приложения показывался синий экран с обрезанным логотипом (каска и кулак
обрезаны, фон синий вместо фирменного). Просьба была узкая — поправить
**только** этот экран, ничего больше не трогать.

**Причина**, установленная диагностикой: это не собственный Flutter-экран
проекта, а системный сплэш Android 12+ (SplashScreen API). Без явной
настройки под него ОС сама собирает заглушку из иконки приложения и
обрезает её в круг без учёта полей — отсюда обрезка и случайный синий фон
на некоторых прошивках (похоже на MIUI/HyperOS).

**Что изменено** (10 файлов, только `android/app/src/main/res/**`):

- Новый `values-v31/styles.xml` — явный фон + иконка для системного сплэша
  Android 12+, чтобы ОС не подставляла свою заглушку.
- Новый `drawable-v26/splash_icon.xml` — иконка сплэша объявлена как
  `adaptive-icon`, это единственный надёжный способ гарантировать, что
  лого не обрежется круглой маской на любой прошивке.
- Новые `mipmap-*/splash_icon_foreground.png` (5 плотностей) —
  перегенерированы из исходного `gpm_logo.png` с запасом полей по краям
  (в исходнике лого было «впритык» к границам, из-за этого и резало).
  Белая подложка-бейдж — тот же приём, что уже на экране входа
  (`login_screen.dart`, не тронут, только повторён стиль).
- Фон сплэша — тёплый бежевый `#EDE9E4` (новый `values/colors.xml`), тот
  же цвет, что у карточки лого на экране входа, а не случайный синий/белый.
- Поправлен старый (pre-Android 12) `drawable/launch_background.xml` и
  `drawable-v21/launch_background.xml` — были просто белым фоном без
  картинки, теперь тот же бежевый фон + логотип по центру, для единого
  вида на старых версиях Android.

Больше ничего в diff'е нет — проверено `git diff --stat` перед коммитом,
только эти 10 файлов под `android/app/src/main/res/`.

### 4.2. Решена проблема локальной Android-сборки (кириллица в пути)

Раньше `flutter build apk` падал ещё до сборки ресурсов, потому что
Windows-профиль пользователя содержит кириллицу
(`C:\Users\Юра\Desktop\gpm_platform\gpm_platform`) — и Android Gradle
Plugin, и Kotlin-компилятор ломаются на не-ASCII сегментах пути. Раньше это
было известное ограничение, сборка не проверялась локально.

**Решение** (подробности и точные команды — в памяти
`gpm_platform_deploy_notes`, раздел про кириллицу):

```powershell
subst G: "C:\Users\Юра\Desktop\gpm_platform\gpm_platform"
$env:PUB_CACHE = "C:\pubcache"
$env:GRADLE_USER_HOME = "C:\gradlehome"
Set-Location G:\
flutter pub get
flutter build apk --release   # или --debug
```

Ключевые нюансы (уже записаны в память, но важны для следующей сессии):

- `subst` монтирует папку проекта на виртуальный диск без кириллицы, но
  сами кэши Flutter/Gradle по умолчанию тоже лежат в `C:\Users\Юра\...` —
  их нужно явно переносить через `PUB_CACHE`/`GRADLE_USER_HOME`.
- `subst` **не переживает перезагрузку** — маппинг диска `G:` нужно
  создавать заново в каждой новой сессии Windows.
- **`pub get` и `build` обязательно в одной команде** — что-то в среде
  (похоже, автозапуск `pub get` от Dart/Flutter-расширения VS Code в
  фоне со стандартным кэшем) между отдельными вызовами перезаписывает
  `.flutter-plugins-dependencies` обратно на путь с кириллицей. Один раз
  это уже сломало release-сборку между вызовами — пересборка одной
  командой сразу всё исправила.
- Куча `Suppressed: IllegalArgumentException: this and base files have
  different roots` от Kotlin incremental-компилятора в логе — это шум,
  не фатально, пока сборка заканчивается строкой `Built ...\app-release.apk`.

**Результат** — оба APK собраны и лежат в
`C:\Users\Юра\Desktop\gpm_platform\gpm_platform\build\app\outputs\flutter-apk\`:

```text
app-debug.apk    146.6 МБ   собран 16.09 11:33
app-release.apk   51.3 МБ   собран 16.09 12:57
```

Оба включают коммит `8d66543` (правки сплэш-экрана). **Важно**:
release-APK подписан **debug-ключом** — в `android/app/build.gradle`
(~строка 34-37) стоит `TODO: Add your own signing config for the release
build`, полноценного релизного keystore для Google Play ещё нет. Для
установки на телефон вручную это не мешает, для публикации в Play —
нужен отдельный keystore (см. раздел 6.4, новая задача).

Путь для пользователя, чтобы скопировать APK на телефон и установить
вручную (выбранный пользователем способ — не через `adb`, USB-отладка не
подключалась):

```text
C:\Users\Юра\Desktop\gpm_platform\gpm_platform\build\app\outputs\flutter-apk\app-release.apk
```

**Не подтверждено пользователем**: установка APK на телефон и визуальная
проверка сплэш-экрана в реальности (не собран APK был протестирован
глазами, только по логике генерации иконки/маски и XML-валидации) — уточнить
в начале следующей сессии.

### 6.4. Новая задача, всплывшая в сессии 16.09 (не начата)

**Релизный keystore для Android.** Сейчас release-сборка подписывается
debug-ключом (`android/app/build.gradle`, `TODO: Add your own signing
config`). Для публикации в Google Play (или для стабильных обновлений

этого нельзя будет выпускать обновления под тем же приложением в Play

## 9. Активная архитектура

```text
CRM -> server-to-server GPM API -> PostgreSQL -> Flutter web/Android

Flutter entrypoint: lib/main.dart
Flutter screens:    lib/screens/**   (lib/client, lib/worker, lib/logist — МЁРТВЫЕ)
Flutter API client: lib/services/gpm_api_service.dart
Chat client:        lib/services/chat_service.dart
Общие хелперы:      lib/utils/order_display.dart, lib/utils/date_time_input_formatters.dart
Android ресурсы:    android/app/src/main/res/**  (сплэш-экран, правки 16.09)
FastAPI backend:    app/app_orders_api.py
Production command: uvicorn app.app_orders_api:app
Database:           PostgreSQL (SQLite для локальных тестов)
```

Backend GPM + PostgreSQL — источник истины по заказам, ownership,
откликам, назначениям, чатам и статусам. CRM — только внешний источник
заявок. Legacy Telegram (`main.py`, `app/handlers/**`, `app/services/**`)
не относится к активному потоку.

**Скоуп заказов по ролям** (`orders_for_user` в `app_orders_api.py`):
клиент видит только `created_by == его username`, логист — только свои по
`logist_owns_order`, исполнитель — доступные + назначенные.

**Изменений в бэкенде/веб-фронте в сессии 16.09 не было** — только
нативные Android-ресурсы, раздел 4.1.
