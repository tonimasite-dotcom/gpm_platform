## 3. Выпущенная возможность досрочно закрыть набор

### 3.1. Бизнес-причина

Логист может найти исполнителей не только через GPM, но и через внешние
источники. Например, в заявке требуется четыре человека, через приложение
найден один, а остальные найдены в других каналах. GPM не должен заставлять
логиста ждать заполнения всех четырёх мест внутри приложения.

### 3.2. Новое поведение

Для опубликованной заявки со статусом `PROCESSED` назначенный логист может
нажать «Завершить поиск исполнителей», если уже подтверждён хотя бы один
исполнитель GPM.

После подтверждения действия backend атомарно:

1. переводит заказ в `IN_PROCESS`;
2. сохраняет всех подтверждённых исполнителей в `assigned_worker_ids`;
3. отклоняет оставшиеся заявки со статусом `PENDING`;
4. записывает `decided_at`, `decided_by` и
   `decision_reason=recruitment_closed` для отклонённых откликов;
5. записывает `recruitment_closed_at` и `recruitment_closed_by` в заказ;
6. создаёт audit event `order_recruitment_closed`;
7. прекращает приём новых откликов обычной проверкой статуса заказа.

Закрытие невозможно, если:

- действует не владелец/назначенный логист;
- заказ не находится в `PROCESSED`;
- ещё нет ни одного подтверждённого исполнителя GPM.

Исполнители, найденные вне GPM, не создаются в приложении искусственно и не
учитываются как аккаунты GPM.

### 4.2. Исходная ошибка чата

При открытии чата исполнителем для CRM-заявки интерфейс показывал:

```text
Ошибка: Bad state: Not Found
```

Корневая причина: идентификатор чата содержит номер заявки, например:

```text
chat-001/26-workerLogist
```

Старые FastAPI-маршруты использовали обычный параметр `{thread_id}`, который
не принимает `/` внутри значения. Все четыре маршрута переведены на
`{thread_id:path}`:

```text
GET   /app-api/me/chats/{thread_id:path}
POST  /app-api/me/chats/{thread_id:path}/messages
POST  /app-api/me/chats/{thread_id:path}/support
PATCH /app-api/me/chats/{thread_id:path}/attention
```

Это соответствует уже применённому подходу для CRM order IDs с `/`.

### 4.3. Один чат на одну заявку

Раньше для одного заказа могли появляться отдельные типы:

```text
clientLogist
workerLogist
clientWorker
support
```

В интерфейсе они назывались, среди прочего, «Координация выхода» и «Клиент по
заказу». Пользователь попросил один чат, названный по заявке.

Новое правило канонического чата:

- заказ, созданный клиентом, использует существующий тип `clientWorker`;
- CRM/external заказ и заказ логиста используют `workerLogist`;
- назначенный логист, владелец-клиент при клиентском заказе и все назначенные
  исполнители работают в одном каноническом чате;
- запрос поддержки не создаёт второй чат, а выставляет
  `requires_attention=true` у того же чата;
- новые дублирующие threads не создаются.

Новая схема БД не требуется. Существующие дублирующие строки не удаляются,
чтобы не уничтожать историю, но backend не выдаёт их и запрещает открывать как
неканонические. История старых дублей автоматически не объединяется; если
когда-нибудь потребуется перенос сообщений, это должна быть отдельная
контролируемая миграция.

Заголовок CRM/external чата вычисляется динамически:

```text
Заявка № 001/26
```

Поэтому уже существующая `001/26` получит новый заголовок после релиза без
изменения строки thread в базе.

### 4.5. Гражданство РФ / Не РФ

В истории найден commit `b3d240e`, где существовал выбор требования
гражданства. Новая реализация возвращает смысл, но использует явно требуемые
пользователем варианты:

```text
РФ
Не РФ
```

В форме создания заказа выбор двухвариантный. В редакторе старых и CRM-черновиков
также сохранено совместимое значение `Необязательно`, потому что старые данные
могут содержать `every/any`.

Нормализация backend:

```text
yes / ru / rf / russian       -> national=yes, nationality=ru
no / non_ru / non-rf / foreign -> national=no, nationality=non_ru
every / any / пусто           -> national=every, nationality=any
```

Совместимость с текстовыми CRM-маркерами сохранена:

```text
Только РФ     -> yes
Только не РФ  -> no
```

Серверная выдача доступных заказов теперь проверяет одновременно:

1. статус `PROCESSED`;
2. город заказа против городов профиля;
3. гражданство заказа против boolean-поля `nationality` профиля исполнителя.

Для заказа `РФ` требуется строго `profile.nationality == true`. Для заказа
`Не РФ` требуется строго `false`. Уже назначенный исполнитель продолжает видеть
свой заказ даже при последующем изменении профиля: назначение и возможность
завершить работу важнее discovery-фильтра.

Та же логика сохранена в demo-режиме. Прямая попытка отклика также повторно
проверяется сервером, поэтому обход фильтра через API запрещён.

## 8. Ручная проверка после будущего релиза

Использовать только синтетические аккаунты и данные.

### Чат `001/26`

1. Назначенный исполнитель открывает раздел чатов.
2. Для `001/26` виден ровно один чат.
3. Заголовок: `Заявка № 001/26`.
4. Чат открывается без `Bad state: Not Found`.
5. Исполнитель отправляет синтетическое сообщение.
6. Назначенный логист видит то же сообщение в том же чате.
7. Логист отвечает, исполнитель видит ответ.
8. Запрос поддержки помечает тот же чат как требующий внимания и не создаёт
   второй канал.

### Представление исполнителя

1. Исполнитель открывает заявку, на которую уже откликнулся.
2. В карточке нет `1 из 2`, `1/2` или другого счётчика прогресса набора.
3. Отображается «Набор исполнителей завершен».
4. Возможность работать внутри назначенной заявки сохраняется.

### Гражданство

1. Создать синтетический черновик с `РФ`, опубликовать.
2. Исполнитель с `Гражданство РФ = да` и совпадающим городом видит его.
3. Исполнитель с `Гражданство РФ = нет` и тем же городом не видит его.
4. Создать синтетический черновик с `Не РФ`, опубликовать.
5. Проверить обратную видимость.
6. Проверить, что прямой отклик неподходящего исполнителя получает отказ API.

### Досрочное закрытие набора из уже выпущенного этапа

Отдельное ручное end-to-end подтверждение после production run #12 в этой
сессии не было явно зафиксировано. Желательно проверить:

1. заявка требует более одного исполнителя;
2. подтвердить одного исполнителя GPM;
3. нажать «Завершить поиск исполнителей»;
4. подтвердить диалог;
5. заявка переходит в работу;
6. назначенный исполнитель сохраняет заявку и рабочие действия;
7. новые отклики невозможны;
8. pending-отклики отклонены.
