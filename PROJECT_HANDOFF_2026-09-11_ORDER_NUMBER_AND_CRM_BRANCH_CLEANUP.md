## 4. Что сделано за сессию 11.09 (батч 4, `c0f0b53`)

### 4.1. Серверный счётчик номеров заказов `APP-NNNNNN`

Закрывает решение пользователя от 09.09 (раздел 6.2 старого хендоффа).

**Бэкенд** (`app/app_orders_api.py`):
- Новая таблица-счётчик `gpm_app_order_number_seq` (одна строка,
  `id=1`/`counter`), создаётся в `init_db()` и для SQLite, и для Postgres.
- `allocate_order_number(connection)` — атомарный
  `INSERT … ON CONFLICT DO UPDATE counter = counter + 1` внутри уже
  открытой блокирующей транзакции, которую `persist_published_order`
  открывает сама (`BEGIN IMMEDIATE` на SQLite; на Postgres достаточно
  штатной неявной транзакции psycopg2 + row lock от `UPDATE`) — отдельной
  блокировки не нужно.
- `normalize_external_order` получил `require_order_number: bool = True`;
  `publish_order_payload` передаёт `require_order_number=actor is None` —
  для CRM/интеграции номер по-прежнему обязателен, для заявок из
  приложения (клиент/логист) — нет.
- `persist_published_order` присваивает номер, когда `actor is not None`
  и `external_order_id` пуст, **до** проверки на существующий номер/409.

**Фронт** (`lib/services/gpm_api_service.dart`):
- `_generateManualOrderNumber()` удалён. `createOrder` больше не
  придумывает номер для заявок из приложения — шлёт `order_number: null`,
  сервер присваивает сам; номер берётся из `published['order_number']` в
  ответе (эта часть уже была на месте с прошлых сессий).
- CRM/внешние заявки (`source: external`) сохранили старое поведение —
  фолбэк на `title`, если номер не передан (не трогали).
- Демо-режим (нет бэкенда) — свой локальный счётчик,
  `_generateDemoOrderNumber()`: сканирует `_demoOrders` на максимальный
  существующий `APP-<n>`, +1.

Тесты: `test_actor_create_without_order_number_gets_sequential_number`,
`test_crm_create_without_order_number_still_rejected` в
`tests/test_app_orders_api.py`.

Формат меняется только для **новых** заказов; старые `APP-…` id остаются
(это PK, миграции данных нет). CRM-заказы сохраняют формат `001/26`.

## 9. Активная архитектура

```text
CRM -> server-to-server GPM API -> PostgreSQL -> Flutter web/Android

Flutter entrypoint: lib/main.dart
Flutter screens:    lib/screens/**   (lib/client, lib/worker, lib/logist — МЁРТВЫЕ)
Flutter API client: lib/services/gpm_api_service.dart
Chat client:        lib/services/chat_service.dart
Общие хелперы:      lib/utils/order_display.dart, lib/utils/date_time_input_formatters.dart
FastAPI backend:    app/app_orders_api.py
Production command: uvicorn app.app_orders_api:app
Database:           PostgreSQL (SQLite для локальных тестов)
```

Backend GPM + PostgreSQL — источник истины по заказам, ownership,
откликам, назначениям, чатам и статусам. CRM — только внешний источник
заявок. Legacy Telegram (`main.py`, `app/handlers/**`, `app/services/**`)
не относится к активному потоку.

**Скоуп заказов по ролям** (`orders_for_user` в `app_orders_api.py`):
клиент видит только `created_by == его username`, логист — только свои по
`logist_owns_order`, исполнитель — доступные + назначенные. Endpoint
`/app-api/me/orders` скоупит, `/app-api/orders` (интеграционный токен) —
нет.

**Новое с 11.09:** таблица `gpm_app_order_number_seq` (счётчик номеров
заказов) и `allocate_order_number()` в `app/app_orders_api.py` — см.
раздел 4.1.
