## Поведение

- Отправленное сообщение сразу отображается в ленте. Поле ввода очищается
  сразу, поэтому текст следующего сообщения не теряется после ответа сервера.
- Состояния сообщения: отправляется, отправлено, не отправлено с повтором.
  «Отправлено» означает подтверждение сервера, а не прочтение собеседником.
- UUID сообщения передаётся как `client_message_id`. Повтор использует тот же
  UUID; сервер возвращает исходную запись. Другой текст или автор с тем же ID
  получает 409. Успешный повтор не добавляет сообщение и audit event заново.
- При потере ответа сервера очередное обновление сверяет сообщения по UUID
  и убирает локальный дубликат/состояние ошибки.
- Открытая переписка обновляется каждые 3 секунды, список — каждые 5 секунд.
  Запросы не накладываются внутри одного экрана. В фоне приложения и под
  другим маршрутом периодическое обновление приостанавливается.
- История остаётся видимой при временной ошибке обновления. Есть повтор и
  автоматическое восстановление. Начальная ошибка тоже имеет кнопку повтора.
- Пока пользователь читает историю, новые входящие буферизуются за кнопкой
  «Новые сообщения», сохраняя положение уже отображаемых сообщений.
- Черновики и исходящие сохраняются в памяти при переходах между чатами,
  отдельно по роли/чату и сессии. Выход из аккаунта меняет область сессии.
  Перезагрузка страницы/перезапуск приложения не сохраняет черновики.
- Enter отправляет, Shift+Enter оставляет перенос строки. На экранной
  клавиатуре сохраняется многострочный ввод; отправка доступна кнопкой.
- Добавлены даты, выделение/копирование текста и поиск по тексту переписки.
  Список показывает последнее сообщение, непрочитанные и поиск по номеру,
  названию заявки или последнему сообщению.
- Свои сообщения определяются серверным `is_own` по аккаунту, а не по роли.
  Демо-режим сохраняет прежнюю модель ролей.

## Сервер и совместимость

Новых таблиц и миграций нет. Используется существующий уникальный message ID.
`client_message_id` необязателен, поэтому старый клиент продолжает отправлять
сообщения. Перед проверкой нового клиента нужно обновить backend: старый
backend не обеспечивает новый контракт повторов и не возвращает `is_own`.
При будущем согласованном выпуске порядок: backend, затем frontend.

GET отдельной переписки больше не перечисляет остальные чаты. Отправка
возвращает именно вставленное сообщение, а не последнюю запись всей истории.
Курсор прочитанного обновляется до полученной истории и не движется назад.
Проверки доступа, канонический чат заявки, CRM-номера со слешем, поддержка
в том же чате и запрет новых сообщений в архиве сохранены.

Обновление реализовано опросом HTTP, не WebSocket. Пока API возвращает всю
историю одной переписки; для больших объёмов следующий технический шаг —
постраничная история и получение только новых сообщений. Вложения, голосовые,
ответы-цитаты, редактирование/удаление сообщений и push-уведомления в эту
доработку не входят.

## Ручная приёмка перед выпуском

На синтетической заявке `001/26` открыть один и тот же чат исполнителем и
назначенным логистом в двух сессиях. Проверить отправку в обе стороны,
несколько сообщений подряд, восстановление после отключения сети, чтение
истории при входящих, поддержку, архив и другой аккаунт исполнителя.
Сравнить утверждённый вид экранов на телефоне и компьютере.
