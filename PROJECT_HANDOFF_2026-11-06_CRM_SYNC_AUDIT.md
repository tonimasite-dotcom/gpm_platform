## Фактические находки

1. Открытые списки/карточки заказов не имеют фонового обновления. Данные
   загружаются при входе, ручном обновлении и после действий. Поэтому CRM
   может уже обновить API, а открытая карточка продолжает показывать старое.
2. Редактор OrderDraftEditScreen отправляет все поля формы. В изолированной
   временной БД воспроизведено: CRM меняет адрес, затем GPM сохраняет старую
   форму, где пользователь изменил только описание, и возвращает старый адрес.
   Статус и назначенные рабочие при этом сохраняются. Это воспроизведение
   касается только вымышленных данных; рабочие заказы не менялись.
3. Устаревшие активные публикации без явной привязки к ts намеренно не могут
   перезаписывать принятые данные. Связывать по совпадению номера запрещено.
4. Сейчас в GPM **нет активных связанных с ts заказов**, нет и активных
   untagged Workstaff-заказов. В ts один старый state-файл для 005/26,
   CRM ID 56797. Заказ ts существует, но GPM-заказ отсутствует, sync GET дает
   404. Последний успешный обмен state: 15.10.2026 10:05:01 UTC.
   Минутный log обновляется (проверено 06.11, 09:33 UTC / 12:33 МСК), последние
   пять результатов: Synced: 0; deferred: 1. Отсутствие заказа не устранялось
   восстановлением/повторной публикацией/удалением state.
5. Поэтому текущую рабочую передачу CRM → GPM → CRM на активной паре нельзя
   подтвердить без предоставленной связанной заявки или согласованной тестовой
   пары. Факт исправности протокола не является приемкой такой передачи.

## Владение полями

| Поля | Действующее поведение |
|---|---|
| Город, адрес/части/координаты, дата-время, количество, часы/минимум, ставка рабочих, описание, метро, дополнительная информация | Общие поля, двустороннее сравнение с последними принятыми значениями |
| Клиентские бюджеты, отдельные разновидности ставок | Особые направления и права по таблице integrations/workstaff-test-crm/README.md; логисту нельзя менять клиентский бюджет |
| Название GPM, гражданство, режим/описание смены | Поля GPM, в существующей CRM нет отдельных соответствующих колонок |
| Статусы, назначения, отклики, табель, оценки, чаты | Процессы GPM; содержательный sync их не заменяет |

Разные поля объединяются. При одновременном изменении одного поля существующий
planner дает приоритет приложению. Устаревший CRM PATCH отклоняется по revision
с HTTP 409. Это действующая политика; менять ее молча в новой задаче нельзя.
Требование синхронизации общих полей не является разрешением копировать целиком
базы, учетные данные, рабочие профили и инфраструктуру двух систем.

## Предлагаемый объем доработки для согласования

### GPM

1. Фоновое обновление видимых списков и карточек по авторизованному API, например
   раз в 20 секунд и при возвращении приложения на экран. При скрытом экране,
   открытой форме/диалоге и активной операции запросы приостанавливаются.
   Ошибка сети сохраняет последний успешный экран и сообщает о несвежих данных;
   ответы старых запросов не заменяют более новые. Фоновые операции не пишут данные.
2. Сохранение только реально измененных, нормализованных полей. Канонизировать
   числа, дату-время/UTC и пустые значения, чтобы само открытие формы не создавало
   ложные правки. Не переписывать свежие поля, которых пользователь не касался.
3. Защита от устаревшего сохранения: сравнить базовые значения именно изменяемых
   полей с текущим заказом в той же транзакции. Если такое поле уже изменилось,
   вернуть конфликт, сохранить ввод пользователя и предложить перечитать заказ.
   Изменения разных полей объединять, одинаковых — не затирать старой формой.
   Табель/оценки не должны создавать ложный конфликт изменения адреса/описания.
4. Сохранить существующие роли и жизненный цикл. Не давать клиенту права логиста,
   логисту — изменение клиентского бюджета, всем — правку закрытых заказов.
   Формы должны отражать разрешенные поля, API остается источником прав.

Ожидаемые файлы: экраны заказов/редактора трех кабинетов, общий механизм
обновления, GpmApiService, обработчик PATCH GPM и соответствующие tests.
Расширение контракта сохранения должно быть совместимым при последовательном
выпуске backend/frontend. Миграции не предполагаются.

### Тестовая CRM и приемка

5. Сохранить явную привязку к ts и существующий защищенный sync-протокол.
   Не менять приоритет конфликтов интеграции без отдельного решения владельца.
   Устаревшую 005/26 диагностировать отдельно; не восстанавливать и не связывать
   автоматически. Любое изменение диагностики/обработки stale state в CRM
   согласовать как отдельную часть объема, не удалять state/backup.
6. Для приемки использовать предоставленную активную связанную заявку либо
   отдельно согласованную синтетическую пару ts/GPM. Согласовать ее создание,
   перечень изменяемых полей и восстановление тестовых значений до записи.
   Проверить обе стороны, открытый экран, старую форму, конфликт одного поля,
   независимые поля, сбой связи, повтор и защиту закрытых заказов.
7. Перед выпуском проверить свежий encrypted backup, пройти Python/PostgreSQL,
   Flutter и PHP-проверки. Развернуть штатным production workflow только
   согласованные GPM-компоненты; любое изменение ts выпускать отдельно и только
   в ее физическом каталоге с проверенными копиями. После проверки записать
   SHA, CI/deploy/backup и остаток ручной приемки.

Последствия: добавятся фоновые чтения API; устаревшую правку иногда придется
повторить после конфликта. Старые рабочие данные не пересчитываются и не
перепривязываются. Откат кода не отменяет уже сохраненных изменений заказа;
восстановление данных требует отдельного согласованного действия и backup.

## Ограничения

Основную CRM менять только после отдельного явного согласования владельца.
Действующая интеграция ограничена `ts.workstaffcrm.ru`. Задача по GPM не разрешает
менять CRM. В этом аудите основная CRM не затронута; тестовая CRM только читалась.

Очистка заявок не разрешает удаление таблиц, схемы, кода, аккаунтов, профилей,
авторизации, приглашений, аудита, конфигурации, секретов, backup и инфраструктуры.
Для изменения жизненно важных компонентов нужны отдельная задача, перечень
объектов, оценка последствий, план восстановления и явное согласование.
Здесь жизненно важные компоненты и рабочие данные не изменялись. Секреты,
пароли и незашифрованные backup не публиковать в Git и логах.
