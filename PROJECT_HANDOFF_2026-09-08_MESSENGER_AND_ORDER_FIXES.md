## 4. Новое: `gh` CLI настроен и авторизован

Раньше (до этой сессии) `gh` CLI не был установлен, деплой запускался только
вручную через GitHub UI (Actions → Run workflow) пользователем. За эту сессию:

- `gh` CLI установлен через `winget install --id GitHub.cli` в
  `C:\Program Files\GitHub CLI\gh.exe` (версия 2.100.0);
- пользователь прошёл `gh auth login` (GitHub.com, HTTPS, browser device
  flow, email-подтверждение sudo mode);
- аккаунт: `tonimasite-dotcom`, token scopes: `gist`, `read:org`, `repo`,
  `workflow`.

Это значит: **в новом чате деплой можно запускать напрямую**, без ручного
клика в UI и без запроса Personal Access Token у пользователя:

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" workflow run deploy-production.yml `
  --repo tonimasite-dotcom/gpm_platform --ref main -f target=all

& "C:\Program Files\GitHub CLI\gh.exe" run watch <run-id> `
  --repo tonimasite-dotcom/gpm_platform --exit-status
```

`gh` может не быть в `PATH` в новой сессии терминала сразу после установки —
если `gh` не находится, использовать полный путь выше или запустить новую
сессию/терминал. Проверить авторизацию:

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth status
```

Это меняет прежнюю заметку в памяти "нет `gh` CLI, использовать GitHub API +
сохранённый токен" — она устарела, `gh` CLI теперь есть и авторизован
постоянно на этой машине.

## 5. Что сделано за эту сессию (полная сводка)

### 5.1. Мессенджер (commit `776d8d0`, задокументирован в `MESSENGER_HANDOFF_2026-09-08.md`)

Полная переработка UX чатов при сохранении палитры/стилистики GPM:

- отправка без перезагрузки переписки, поле ввода очищается сразу;
- статусы «отправляется/отправлено/не отправлено» с retry без дублей через
  `client_message_id` (UUID), сервер возвращает исходную запись при повторе;
- входящие сообщения появляются автоматически (опрос: открытый чат каждые
  3 сек, список чатов каждые 5 сек — не WebSocket);
- черновики сохраняются в памяти при переходах между чатами (по роли/чату/
  сессии, не переживают перезагрузку страницы);
- стабильная прокрутка, кнопка «Новые сообщения» при чтении истории;
- Enter отправляет, Shift+Enter — перенос строки;
- даты, выделение/копирование текста, поиск по чатам;
- последнее сообщение и непрочитанные в списке чатов;
- «своё» сообщение определяется server-side `is_own` по аккаунту, а не по
  роли (фикс: раньше в чате с несколькими исполнителями чужие сообщения
  могли выглядеть как свои).

Тесты на момент коммита: 27 Flutter + 44 backend (1 PostgreSQL-only skip),
`flutter analyze` чисто, web build собран.

### 5.2. Семь правок по списку пользователя (commit `3b42d2c`)

1. **Адрес/метро у исполнителя в списке заявок** — раньше карточка показывала
   пустую строку (📍 без текста), потому что backend намеренно вырезал адрес
   для неназначенного исполнителя (защитная мера из аудита 25.08). По явному
   уточнению пользователя это отменено: `order_for_user` в
   `app/app_orders_api.py` больше не прячет `address`/`address_street`/
   `address_number`/`address_lat`/`address_lon` для роли `worker`. Карточка
   в `lib/screens/worker/worker_orders_screen.dart` (`_LocationLine`) теперь
   всегда показывает и адрес, и метро, если данные есть.
2. **Десинхронизация количества людей** (в одной роли «3 человека», у
   исполнителя «0/1») — найдена реальная причина: при повторном CRM-импорте
   того же номера заявки `merge_existing_workflow_state` сохраняла только
   workflow-поля (`status`, `assigned_worker_ids`, ...), а все
   редактируемые поля (`workers_count`, `address`, цены и т.д.) тихо
   перезаписывались значениями из свежего CRM-payload, отменяя локальные
   правки логиста. Исправлено: после публикации (`status != NEW`) все поля
   из `ORDER_DRAFT_EDITABLE_FIELDS` теперь тоже сохраняются из `existing` и
   не перезаписываются повторным импортом. **Это изменение политики
   синхронизации** — если повторный CRM-импорт должен был иметь приоритет
   над локальными правками после публикации, это нужно явно обсудить и
   переиграть.
3. **Логист не может редактировать цены** — `individual_price`/
   `legal_price` заблокированы для роли `logist` и на сервере
   (`LOGIST_RESTRICTED_DRAFT_FIELDS`, 403 при попытке отправить эти поля в
   PATCH), и в форме (`OrderDraftEditScreen(isLogist: true)` из
   `logist_orders_screen.dart` — поля показываются, но задизейблены).
4. **«Необязательно» → «Любое»** в дропдауне гражданства в
   `order_draft_edit_screen.dart`.
5. **Задвоенное поле «Часы»** в редакторе заявки убрано, остаётся только
   «Минимальное время оплаты, ч»; при сохранении это же значение шлётся и
   как `hours`, и как `min_time`.
6. **Автоподстановка даты/времени** — новый переиспользуемый
   `DigitGroupInputFormatter` в `lib/utils/date_time_input_formatters.dart`,
   применён в создании заявки клиентом, редакторе заявки и в дате
   рождения/дате выдачи паспорта в профиле исполнителя.
7. **Степпер «Часы (1-24)»** у клиента при создании заявки переименован в
   «Минимальное время оплаты» — подтверждено, что оба поля (`hours` и
   `min_time`) всегда заполняются одним и тем же значением из этого
   степпера, отдельного понятия «ориентировочный объём работ» в проекте нет.

Новые backend-тесты: `test_logist_cannot_edit_client_facing_prices`,
`test_republished_order_keeps_locally_edited_content` в
`tests/test_app_orders_api.py`. На момент коммита: 47 backend-тестов
(1 PostgreSQL-only skip), 27 Flutter-тестов, `flutter analyze` чисто.

## 7. Активная архитектура

```text
CRM -> server-to-server GPM API -> PostgreSQL -> Flutter web/Android
```

```text
Flutter entrypoint: lib/main.dart
Flutter screens:    lib/screens/**
Flutter API client: lib/services/gpm_api_service.dart
Chat client:        lib/services/chat_service.dart
FastAPI backend:    app/app_orders_api.py
Production command: uvicorn app.app_orders_api:app
Database:           PostgreSQL
```

Backend GPM и PostgreSQL — источник истины по заказам, ownership, откликам,
назначениям, чатам и статусам. CRM — только внешний источник заявок (и,
после фикса из раздела 5.2, больше не может тихо перезаписать локально
отредактированные поля уже опубликованной заявки).

Legacy Telegram (`main.py`, `app/handlers/**`, `app/services/**`) не
относится к активному production-потоку.
