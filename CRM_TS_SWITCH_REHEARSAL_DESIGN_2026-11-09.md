# Схема предстоящей репетиции переключения ts

Статус: проект исполнения, не готовый установщик и не отчет о репетиции.
Применение к работающей ts не разрешено этим документом. Основная CRM исключена.
Общий объем уже согласован; эти технические действия сначала реализуются и
проверяются вне работающих CRM, затем последствия показываются владельцу.

## Выбранный способ сохранить возможность отката

Использовать отдельную новую БД для обновляемой версии. Исходная БД и полный
снимок файлов сохраняются. На MySQL 5.7 общий rollback DDL не дает восстановления,
а down финансовых миграций может запрещать откат или удалять историю.
Ни текущие, ни прежние таблицы/аккаунты/снимки ради отката не удаляются.

Во время закрытого окна исходная БД заморожена: после остановки всех ts-писателей
создается финальный согласованный encrypted checkpoint. В новую пустую БД
восстанавливаются только данные ts, затем применяется точный проверенный список
адаптаций. Старое дерево кода/собственных файлов остается нетронутым экземпляром.
Сохранение БД/файлов на этом этапе не подразумевает их автоматическое удаление позже.

Для репетиции нужны два отдельных private DB/datadir и две файловые версии,
размещенные в новом каталоге. Существующие rehearsal-mysql, sql-recovery,
candidate и file-recovery не заменять, не переинициализировать и не использовать
как место разрушительного восстановления. Сохраненную recovery-БД разрешено
читать как источник; копирование ее offline-файлов требует штатной остановки
и проверки отсутствия процесса, сокета и незавершенного копирования.

## Обязательный контекст репетиции

Runtime-проверки должны знать конкретные новые private root, DB, account, socket,
datadir, maintenance, CLI и network namespace. Существующий GpmTsRehearsal знает
только старый candidate: он сейчас откажет в новой среде. До запуска нового
runtime нужен явный отдельный контекст с теми же проверками и negative-тестами.
Не выдавать новый каталог за live ts через APP_URL, symlink, bind mount или
отключение guards. Не править сохраненный candidate для обхода отказа.

Bootstrap старой версии тоже должен иметь явную private-идентичность для
ts-only участков входа, редактора ставки и model guard. Если эти участки просто
не активировались из-за другого base_path, это не успешная приемка старой версии.
Проверки context-инструментов включают отсутствие network isolation, чужой
root/DB/account/socket/datadir, непустую цель восстановления и повторный запуск.

## Активации и настройки как часть версии

WorkerCalculationActivation и PlanningDayActivation подписывают root/env/DB/
account/host/port. Простое копирование marker-файла в новую DB-идентичность
не работает; отказ проверен на реальных классах. Подпись или identity guard
не отключать. Новая версия получает собственную локальную границу и корректную
подпись своей идентичности; границы основной не читаются и не копируются.

Для worker boundary проверить согласованность файла с boundary-строкой
order_worker_calculations. Для planning day использовать следующий уже не
выданный ID минус один, не только MAX(id): незавершенные и откаченные INSERT
могут сдвинуть AUTO_INCREMENT. Существующий PlanningDayBoundary публикует marker
под LOCK TABLES; его guard знает main/test и еще не поддерживает ts/private.
Его адаптация и проверка частного запуска еще нужны. Команда пока не запускалась.

Старые заказы остаются со старым правилом; id, выданные после cutover, получают
день по поясу заказа. У кандидата реальный planning marker пока отсутствует:
новое правило проверено только на отдельных synthetic markers, не активировано
для кандидата. Worker marker кандидата также не менялся.

Конфигурация/секреты ts сохраняются отдельно от пакета кода. Не брать .env,
JWT/APP key или токены основной; не подменять их значениями rehearsal. Не
публиковать содержимое .env/marker/ключей в Git и логах. Для новой DB потребуется
своя учетная запись с правами только на нее; срок хранения прежней не меняется.

## Последовательность репетиции и отказов

1. Создать новые private-слоты и зафиксировать исходные code/vendor/assets,
   DB schema/данные, activation/state, ownership/modes/links. Проверить ключ
   recovery и диск; без исходной полноты не переходить к переключению.
2. Выполнить smoke старой версии на синтетических данных через ее реальный
   private runtime. Откатить транзакции, закрыть всех private-писателей.
3. Восстановить checkpoint в новую пустую DB, применить адаптации по manifest,
   создать собственные активации и сверить все исходные строки/финансовые итоги.
4. Переключить только private runtime на новую файловую/DB-версию. Предпочтительно
   атомарное переключение с сохранением обоих деревьев; если платформа этого не
   поддерживает, заранее проверить отказ и восстановление в промежуточном состоянии.
5. Проверить новую версию: вход/права/формы/документы/финансы, типовые старые v1 и
   новые v2, stale-формы, пути хранения, marker identity и отсутствие внешних отправок.
6. Смоделировать отказ после части миграций и отдельно после переключения кода,
   пока новые записи/sync закрыты. Вернуть исходные DB + code + собственные
   файлы/настройки/markers, проверить их хеши и работающий runtime старой версии.
   Не считать сверку одного архива полной репетицией отката.
7. После возврата повторно сверить данные, роли/учетные записи/аудит и исходные
   файлы. Новые неудачные экземпляры сохранить для разбора. Выключить частные
   MySQL, подтвердить отсутствие их процессов/сокетов и сохранность datadir.

Все временные синтетические записи откатываются транзакциями. Сгенерированные
документы/fixture-файлы сохраняются как частные доказательства, без публикации.

## Что дополнительно требуется для реального окна

- Read-only preflight именно ts: ожидаемые root/env/DB/account/socket/schema,
  полное покрытие файлов и свободное место, содержимое writer-пускателей и
  активные соединения только ts. Полный live apply/preflight еще не реализован.
- Закрыть web и остановить только ts cron/очереди, дождаться начатых операций.
  Не останавливать общие nginx/PHP-FPM/MySQL/cron/Redis и задачи основной.
  Общий Laravel scheduler не включать: в новом Kernel есть внешние автоматы.
- Разобрать настройки FPM/opcache именно ts и способ обновления кеша без общего
  reload. Это еще не проверено; атомарная замена файлов сама не доказывает смену
  исполняемого PHP-кода. Новые assets/manifest и старые вкладки проверить отдельно.
- Live public/storage указывает в отдельную test.workstaffcrm.ru. Цель ссылки
  не копировалась и не читалась в этой подготовке. Сохранение самой ссылки не
  доказывает покрытие ее внешней цели резервной копией. Не менять ее молча.
- Финальный checkpoint создается после остановки писателей. Online backup
  09.11 восстановлен и проверен, но не заменяет этот checkpoint.
- Возобновление существующего sync заканчивает возможность автоматического
  возврата к старой DB: могут появиться новые записи/внешние эффекты. После этого
  нужен новый разбор сохранения изменений, а не автоматический restore.

Измерить отдельно: остановку и ожидание писателей, финальный backup, restore,
миграции/DDL, переключение, закрытые проверки, полный возврат и повторные проверки.
Время отдельных acceptance-тестов не является оценкой простоя. До получения
этих замеров окно владельцу не обещать. После успешной репетиции собрать один
конкретный пакет с auth/API permission fixes и запросить согласование применения.

Основную CRM не менять. Очистка заявок не разрешает удаления схемы, таблиц,
кода, учетных записей, профилей, авторизации, приглашений, аудита, конфигурации,
секретов, backup и инфраструктуры; правило действует и для репетиции/отката.
Изменения жизненно важных live-объектов требуют перечня, последствий,
плана восстановления и явного согласования. Новые правила sync — отдельная задача.
