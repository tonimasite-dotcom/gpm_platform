# Регистрация по приглашению

Регистрация GPM остаётся закрытой. Открытой формы, где любой посетитель может
сам выбрать роль и создать аккаунт, нет. Владелец заранее создаёт одноразовые
приглашения, а пользователь самостоятельно устанавливает пароль.

## Один тестировщик в трёх ролях

Один человек получает три независимых аккаунта:

- `<prefix>-client` — клиент;
- `<prefix>-worker` — исполнитель;
- `<prefix>-logist` — логист.

Это сохраняет серверную изоляцию ролей и позволяет проверить реальные
permission-сценарии. Переключение роли внутри одной сессии не используется.

## Создание приглашений

Команду запускают только на защищённом backend-сервере с уже загруженным
production environment:

```bash
python -m app.account_invite_cli create-test-user \
  --prefix tester-001 \
  --created-by project-owner \
  --output /root/gpm-app-invitations-tester-001.json
```

Путь вывода обязан быть абсолютным и находиться вне Git-репозитория. CLI
создаёт файл с mode `600`, не печатает коды приглашений в терминал и выводит
только роли с логинами. Файл содержит секретные одноразовые коды; его нельзя
добавлять в Git, чат, issue, Actions artifact или frontend `.env`.

Приглашение действует три дня. Создание нового приглашения для того же логина
отзывает прежнее неиспользованное приглашение.

## Действия пользователя

1. Открыть приложение и выбрать нужную роль.
2. Перейти на вкладку «Регистрация».
3. Вставить соответствующий одноразовый код.
4. Задать и повторить пароль длиной от 12 до 256 символов.
5. После создания аккаунта войти с показанным логином и выбранным паролем.
6. Для другой роли выйти и повторить процедуру с другим приглашением.

Роль и логин берутся только из серверного приглашения. Несовпадение роли,
истёкший, отозванный или уже использованный код отклоняются. В БД хранится
только SHA-256-хеш кода, а пароль хранится только как versioned `scrypt`-хеш.
Создание, успешное использование и отклонённые попытки записываются в audit log.

## Production-порядок

Эта возможность не является разрешением на deployment. Перед первой публикацией
нужны обычные database/env backups, CI, проверка rollback и явное подтверждение
владельца. После публикации сначала создаются приглашения только для одного
тестировщика и используются исключительно синтетические данные.

Файлы с приглашениями и таблицу `gpm_app_account_invitations` не удалять до
решения по retention и возможному legal hold. Использованные коды повторно не
активируются.
