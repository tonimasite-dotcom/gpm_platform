### 6.1. ЗАБЛОКИРОВАНО — нужны ответы пользователя

**P0-3. Оценка исполнителя «С нареканиями».**
Логист на экране «Оценка исполнителя» (заказ в статусе `DONE_PENDING`)
жмёт одну из 4 кнопок: «Справился» / «Не справился» / «Нейтрально» /
«С нареканиями». Проблемы:
- В **API-режиме** `completeOrderWithResult`
  (`lib/services/gpm_api_service.dart`) просто делает
  `updateOrderStatus(orderId, 'CONVERTED')` и **выбрасывает** `result`.
  Бэкенд-эндпоинта для записи оценки **нет** — переход
  `DONE_PENDING → CONVERTED` это обычный патч статуса. Рейтинг/счётчики
  меняются **только в demo** (`gpm_api_service.dart`, switch по `result`).
- Ярлык «С нареканиями» шлёт value `good`, что в demo даёт **+1 к
  рейтингу**. Пользователь сказал: «с нареканиями — между плохо и
  хорошо», т.е. это лёгкий минус, не плюс.

Согласовано направление: новый value `complaint` (−1 рейтинг, **без**
засчитывания срыва), осиротевший `good` убрать. **Ждём:**
- **A1** — точная величина изменения рейтинга для `complaint` (−1? другое?).
- **A2** — делать ли серверный эндпоинт записи оценки сейчас (это
  `target=all`, миграции нет, но нужен новый маршрут + RBAC логиста +
  запись в профиль исполнителя), или сначала только demo-маппинг + ярлык.

### 6.2. Решено пользователем, отдельными задачами

**Номера заказов — серверный счётчик `APP-NNNNNN`.**
Сейчас клиент генерит `_generateManualOrderNumber()` =
`APP-<ггммдд>-<ччммссмс>` локально и шлёт как `order_data.order_number`,
который на бэкенде становится **первичным ключом** заказа (`id`) и корнем
id чатов/начислений. Это подвержено коллизиям. Решение: серверный
сквозной счётчик, 6 цифр с нулями, глобальный (не по годам).
Нужно:
- бэкенд: миграция + счётчик (SQLite + Postgres), присвоение номера
  внутри транзакции `persist_published_order`, когда заказ создан из
  приложения (`actor is not None`) и номер не передан;
- `normalize_external_order` делает `order_number` необязательным для
  actor-создания (для CRM/интеграции — по-прежнему обязателен);
- фронт: перестать генерить, брать `published['order_number']` из ответа;
  demo-режим — локальный счётчик;
- деплой `target=all`.
Формат меняется только для НОВЫХ заказов; старые `APP-…` остаются (это
PK, миграции данных нет). CRM-заказы сохраняют формат `001/26`.
Промежуточно уже сделано (батч 2): полный номер в шапке у исполнителя.

**P2-18. Чистка экрана деталей заказа.**
Пользователь выбрал делать **одной отдельной задачей**, не быстрым
фиксом. Экраны деталей у исполнителя и логиста: плоский список ~15 строк
`_OrderFact` (3 разные «Ставка …», пустые поля, тройной повтор номера:
шапка + заголовок + строка «Номер заказа:»). Нужно решить с
пользователем состав и порядок полей по ролям. Компоновку по
DESIGN_FREEZE не менять, состав/порядок полей — можно.

**C (несколько исполнителей + «Завершить заказ»).** Оставить как есть —
заказ уходит на подтверждение целиком. Изменений не вносить.

## 8. Активная архитектура

```text
CRM -> server-to-server GPM API -> PostgreSQL -> Flutter web/Android

Flutter entrypoint: lib/main.dart
Flutter screens:    lib/screens/**   (lib/client, lib/worker, lib/logist — МЁРТВЫЕ)
Flutter API client: lib/services/gpm_api_service.dart
Chat client:        lib/services/chat_service.dart
Общие хелперы:      lib/utils/order_display.dart, lib/utils/date_time_input_formatters.dart
FastAPI backend:    app/app_orders_api.py
Production command: uvicorn app.app_orders_api:app
Database:           PostgreSQL (SQLite для локальных тестов)
```

Backend GPM + PostgreSQL — источник истины по заказам, ownership,
откликам, назначениям, чатам и статусам. CRM — только внешний источник
заявок. Legacy Telegram (`main.py`, `app/handlers/**`, `app/services/**`)
не относится к активному потоку.

**Скоуп заказов по ролям** (`orders_for_user` в `app_orders_api.py`):
клиент видит только `created_by == его username`, логист — только свои по
`logist_owns_order`, исполнитель — доступные + назначенные. Endpoint
`/app-api/me/orders` скоупит, `/app-api/orders` (интеграционный токен) —
нет.
